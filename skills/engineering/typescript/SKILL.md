# TypeScript

For implementation, design decisions, debugging, or engineering review, also use "engineering". For a routine lookup or straightforward explanation, answer from the source without loading this standards table or engineering.

| Rule                            | Summary                                                                                                                                                                                                                                                                              |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Discriminated unions            | Model variants with a `kind` literal discriminant so impossible states can't be represented. No optional-field bags.                                                                                                                                                                 |
| Branded types                   | Brand primitives with `& { readonly __brand: "X" }` so they can't be mixed up. Validate once at creation.                                                                                                                                                                            |
| Constructive modelling          | Choose representations that remove invalid combinations. Use `[T, ...T[]]` for non-empty, `[T, T][]` for pairs, and `start` plus a validated duration for a range. Type structure owns structural invariants. Runtime validation owns numeric constraints TypeScript cannot express. |
| Simplest total type             | Keep `T[]` while every operation on it stays total. Strengthen to `NonEmpty<T>` only where the loose type forces `!`, a cast, or a "should never happen" throw.                                                                                                                      |
| `unknown` over `any`            | External data is `unknown`. `any` disables type checking everywhere it touches.                                                                                                                                                                                                      |
| Avoid unchecked `as` assertions | An assertion bypasses type checking and can hide a runtime bug. Prefer narrowing or `satisfies`. Assert only after validation or when expressing a proven invariant TypeScript cannot infer. Put a non-local proof in a named guard, parser, or assertion function, not a comment.   |
| Narrowing hierarchy             | Discriminant switch > `in` operator > `typeof`/`instanceof` > user-defined type guard > `as`. Use `typeof` on values whose type is already a known union, not to probe external data; parse that with a schema at the seam.                                                          |
| Type guards                     | Must verify the claim. A lying guard is worse than `as` because the bug hides behind a name that says it's safe. Name them `isX` or `hasX`.                                                                                                                                          |
| Exhaustiveness                  | Inline `const _exhaustive: never = x;` in default arms so the compiler errors when a new variant is added.                                                                                                                                                                           |
| `satisfies` over `as`           | Validates the value without widening literal types.                                                                                                                                                                                                                                  |
| Seam validation                 | Parse where data crosses in, into a named domain type. `Record<string, unknown>` (however spelt) stops at that parse. Trust types inside. Read the engineering skill's design reference for seam placement.                                                                          |
| Schema-derived types            | Reach for `Pick`/`Omit`/`Parameters`/`ReturnType`/`Awaited`/`typeof` before declaring a new interface.                                                                                                                                                                               |
| Object args                     | Pass objects, not positional, so argument order is self-documenting. Skip on hot paths (per-frame render, tokenisers, parsers).                                                                                                                                                      |
| Explicit API states             | Avoid boolean control parameters and `Partial<T>` inputs unless those shapes are the domain. Use named options or variants, and keep absence with the caller that understands it.                                                                                                    |
| Expected failures               | Apply the engineering skill's failure guidance. Use the established result type or the smallest discriminated union. Do not add a result dependency as part of an unrelated change.                                                                                                  |
| Strict configuration            | Prefer `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride`, and `noFallthroughCasesInSwitch` for new projects. Treat changes in an existing project as a deliberate migration.                                                                  |
| Precise modules                 | Prefer modules named after the value or capability they own. Avoid catch-all `utils.ts`, `helpers.ts`, `common.ts`, and `misc.ts` files.                                                                                                                                             |
| Real tests                      | Don't mock what you can run. Prefer the framework's real test primitives with leak checks and disposable resources. Verify UI in a running build. Mock only what you can't run locally.                                                                                              |
| Structured telemetry            | Prefer structured logger diagnostics with enough safe context to debug from an id. Keep secrets and raw sensitive payloads out of errors, logs, traces, and snapshots. No `console.log` in shipped code.                                                                             |
