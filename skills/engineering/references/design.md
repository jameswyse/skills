# Design

## Redesign from the requirement

When a new requirement challenges the current design, design as if the requirement had existed from the start. Keep constraints that still matter, not structure that merely exists. Describe the core types and data shapes the requirement calls for, trace how each caller reads and changes them, then find the smallest coherent migration. The result expresses the requirement through its types, state ownership, and interfaces, not through caller coordination or a special-case layer. State the chosen foundation, the rejected alternatives, and the implementation sequence.

Special cases mark requirements the design never accounted for: an `if` for one value, a parameter only one caller understands, a swallowed exception, a retry or sleep, a disabled test. When several cluster around one concept, look for the single change to types, ownership, or interfaces that makes them unnecessary, which often looks nothing like any of them, instead of patching each. Keep a special case only when the redesigned system still needs it.

## Depth and seams

- **Deletion test.** A module earns its place when deleting it would make its decisions and coordination reappear across callers. Deepen when callers repeat the same decisions, ordering, validation, or recovery, when bugs arise in coordination between callers and helpers, or when tests must reproduce caller coordination. Being in-process, having a test replacement, or spanning several files is not a reason, and clear local code that is easy to change stays as it is.
- **Real seams.** A seam needs two necessary implementations, or an existing network, storage, or third-party boundary. A fake built to justify a port doesn't count, and one production adapter behind an interface no caller varies is usually indirection. A deep module keeps its internal seams private.
- **Change history.** Git history shows what actually changes together. Files that repeatedly change in the same commits share a decision that may need one owner. Confirm each lead in the code.
- **Dependency categories.** They decide how a deepened module is built and tested, not whether to deepen. In-process needs no adapter. Local-substitutable uses a local replacement such as PGLite or an in-memory filesystem inside the module's own tests, and keeps that seam internal. Remote and owned gets a port only when the transport varies or must be replaced in tests, with an HTTP, gRPC, or queue adapter in production and an in-memory adapter in tests. External and unowned gets a port at the existing seam, with vendor representations inside the production adapter and a focused fake in tests.
- **Ports.** Define them in the consumer's language, with domain inputs, outputs, and failures, never wire, storage, or SDK representations. Before adding an adapter, reuse a cohesive one through the narrow type the consumer needs, or extend it when the operation changes for the same reason. Don't split it into one-method wrappers.
- **Tests.** Test through the interface. When deepening replaces shallow modules, cover the old observable cases through the new interface and delete tests of superseded helpers and internal state. Keep an internal test only for an independently useful algorithm the interface tests can't diagnose.
